# CLAIMS_REGISTER.md

## Purpose
This register documents required product claims, their current status, and the evidence needed to support them.

## Claim classification legend
- IMPLEMENTED: supported by code and tests in the repository
- SIMULATED: represented in fixtures or demos but not production-validated
- PLANNED: intended but not yet implemented
- EXPERIMENTAL: exploratory and not ready for product claims

## Approved product boundaries
- Initial data source: disclosed synthetic replay fixtures only
- Initial implementation: TypeScript domain engine and fixtures only
- No backend, no dashboard redesign, no LLM integration in the initial milestone
- No public performance claims until benchmark code is implemented
- Deterministic explanations are tested in Milestone 7
- LLM-unavailable behavior is tested only in Milestone 12
- No earlier milestone may require an installed LLM SDK

## Required claim register

### Claim: context-aware behavioral detection
Status: PLANNED
Required evidence: baseline feature specification, event schema, and tests covering context explanation and residual risk.
Public use: allowed only as a planned capability description, not a validated claim.

### Claim: separation of raw deviation, context coverage, and residual risk
Status: PLANNED
Required evidence: UI contract, scoring rules, and scenario test coverage.
Public use: allowed only as part of the product vision.

### Claim: deterministic and inspectable scoring
Status: PLANNED
Required evidence: deterministic scoring functions and test coverage for edge cases.
Public use: allowed only when the calculation exists and is documented.

### Claim: no LLM dependency for risk calculation
Status: IMPLEMENTED as a design boundary, not as a validated system property
Required evidence: architecture boundary and tests prohibiting LLM-influenced scoring.
Public use: allowed as a product principle, not as a maturity claim.

### Claim: explainable residual risk with evidence IDs
Status: PLANNED
Required evidence: evidence identifiers and deterministic explanation fallback.
Public use: allowed only if output explicitly references evidence and uncertainty.

### Claim: supports role and peer-cohort baselines
Status: PLANNED
Required evidence: baseline schema and tests for cold-start and role-change scenarios.
Public use: allowed only in planned or visionary language.

### Claim: supports partially explained context coverage
Status: PLANNED
Required evidence: context compatibility tests and scenario-level acceptance cases.
Public use: permitted only with explicit demonstration wording.

### Claim: can detect compromised accounts
Status: SIMULATED
Required evidence: demo scenario fixtures and evaluation cases only.
Public use: allowed only as a demo scenario, not as a performance statement.

### Claim: live integration with enterprise telemetry
Status: PROHIBITED for current scope
Reason: unsupported not because of technical impossibility, but because the approved data source is synthetic replay fixtures only.

### Claim: zero false positives
Status: PROHIBITED
Reason: unsupported and forbidden under the product governance rules.

### Claim: autonomous containment
Status: PROHIBITED
Reason: out of scope and unsupported without implementation and governance evidence.

### Claim: production readiness
Status: PROHIBITED for current scope
Reason: not supported without explicit deployment and validation evidence.

### Claim: court-admissible evidence
Status: PROHIBITED
Reason: unsupported legal and technical claim.

### Claim: blockchain immutability of evidence
Status: PROHIBITED unless implemented and validated
Reason: must not appear as a product claim without supporting evidence.

### Claim: live benchmark performance
Status: PROHIBITED for now
Reason: public performance claims are forbidden until generated by implemented benchmark code.

## Governance rule
Every visible metric must identify its calculation or data source. Any metric without provenance must be treated as unsupported.

## Open decisions required
- production retention defaults
- alert-budget value for a real deployment
- minimum benchmark performance for public claims
- whether the optional LLM milestone will be approved
- exact performance evaluation plan to be adopted
- how exact benchmark numbers will be sourced and labeled
- whether publicly visible docs may mention simulated demo results
- which claims are product-ready versus demo-only
