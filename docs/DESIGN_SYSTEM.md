# DESIGN_SYSTEM.md

## Design intent
The interface should preserve the successful Obsidian migration aesthetic while shifting the product story from an external attack simulation to a behavioral investigation system.

## Design rule
No application redesign is permitted during documentation and engine milestones. UI migration is permitted only beginning with the approved application-shell milestone.

## Preserved design elements
- dark operational aesthetic
- cyan, amber, red, and violet state language
- Auralis canvas atmosphere
- selective Spline usage
- motion system and replay behavior
- evidence-stream presentation patterns
- risk visualization techniques

## Replaced design elements
The following are intentionally removed or de-emphasized from the product narrative:
- global attack map as the central experience
- external APT narrative framing
- honeynet and digital-twin claims
- decorative blockchain ledger
- fictional performance metrics
- unsupported competitor comparison table
- excessive cyberpunk terminology
- any claim that externalized threat attribution is the core product

## Signature interaction
The central interface is a Shift Graph connecting:
- user
- time
- device
- resource
- privilege
- destination
- contextual approval
- detected change point

The Shift Graph is planned for Milestone 11. Before then, only the design contract exists. Every graph element and explanation must link back to underlying evidence.

## 3D guardrail
3D is optional and later. It must not obscure exact values or evidence. It is not required for the initial product.

## Visual system

### Color language
- cyan: nominal or healthy operational signal
- amber: caution / partial uncertainty
- red: materially unexplained risk or high-risk signal
- violet: context or approved transformation state

### Typography
- technical, operational, and evidence-oriented
- legible in dense investigation views
- consistent with the existing dark environment

### Motion
- motion should support comprehension, not decoration
- respect `prefers-reduced-motion`
- avoid heavy animation for high-frequency investigative data

## Accessibility requirements
- maintain keyboard-accessible controls
- ensure color is not the only discriminator for state
- provide text labels for critical status changes
- maintain sufficient contrast for investigation surfaces
- ensure dense data tables remain navigable
- support reduced-motion behavior and evidence navigation

## Privacy and responsible use
- pseudonymous identities by default
- role-based access assumptions
- data minimization
- configurable retention
- prevention of sensitive message-content exposure
- uncertainty display
- contestability and correction of context
- safeguards against feedback poisoning
- prototype data lasts only for the demo session

## Motion and 3D guardrails
- 3D and dynamic visual scenes should support investigation clarity, not decorative spectacle
- any motion-heavy or 3D treatment must remain secondary to the evidence and explanation layers
- all major claims must still be interpretable without relying on the visual scene alone
- 3D is not required for the initial product and must not reduce evidence precision

## Open design decisions
- final visual token values require approval
- exact dashboard layout rules for the Shift Graph require approval
- acceptable motion intensity for analyst review needs confirmation
- whether evidence metadata is always visible in the graph needs decision approval
- whether the optional LLM narrative layer will be approved later
