# AGENTS.md

## Purpose
This repository is the working baseline for the Obsidian migration and the future Silent Shift product work. This file is the permanent operating contract for all coding agents.

## Core rules

1. Do not modify source files under src/ unless explicitly requested and approved.
2. Do not modify package.json or package-lock.json unless explicitly requested and approved.
3. Do not modify configuration files, build tooling, or environment setup unless explicitly requested and approved.
4. Do not install new dependencies without explicit approval.
5. Do not begin implementation work for product features unless the task is clearly documentation-only or explicitly approved.
6. Preserve the existing working migration baseline. Do not redesign the UI or alter application behavior.
7. Keep product claims grounded in implemented or explicitly simulated capability status.
8. Never infer malicious intent, guilt, or personal blame from raw behavioral anomalies.
9. Never claim production readiness, live integrations, or benchmark performance unless the evidence exists in the repository and is clearly labeled.
10. If a requirement is uncertain, record it as a decision required rather than assuming it.
11. No application redesign is permitted during documentation and engine milestones. UI migration is permitted only beginning with the approved application-shell milestone.

## Approved decisions

### Behavioral telemetry domains
- authentication
- file/resource access
- privilege activity

### Organizational context records
- role changes
- project assignments
- approved travel
- maintenance windows
- temporary access grants

Contextual approval records are not equivalent to behavioral activity and must not be interpreted as behavioral telemetry.

### Initial data source
- disclosed synthetic replay fixtures only
- no live enterprise ingestion claim

### First implementation
- TypeScript domain engine and fixtures only
- no dashboard redesign
- no backend
- no LLM integration

### Context outcomes
- EXPLAINED: all material anomalous evidence is covered by valid context.
- PARTIALLY_EXPLAINED: some material evidence is covered and some remains.
- UNEXPLAINED: no applicable context covers material evidence.
- INDETERMINATE: evidence or context quality is insufficient.

These outcome states must not be defined by arbitrary percentage thresholds.

### Prototype persistence
- in-memory/session-only
- durable audit storage is PLANNED

### Public performance claims
- none until generated by implemented benchmark code

### Shift Graph
- design contract exists before implementation
- first production milestone for the 2D evidence-linked temporal visualization is Milestone 11
- 3D is optional and later
- 3D must not obscure exact values or evidence

### LLM boundary
- deterministic explanations are tested in Milestone 7
- LLM failure behavior is tested only in Milestone 12
- no earlier milestone may require an installed LLM SDK
- optional grounded narrative layer requires separate approval

### Testing
- Vitest may be added in the first coding milestone
- it must be the only new dependency group unless another dependency is separately justified

### Context corrections
- analysts may propose corrections
- corrections must produce audit events
- historical raw deviation must never be erased

### Retention
- configurable retention is a production requirement
- prototype data lasts only for the demo session

### Autonomous containment
- out of scope for the product at this stage

## Required product stance
Silent Shift is a context-aware behavioral-security investigation system.

It detects meaningful behavioral transitions, reconciles them against legitimate organizational context, and prioritizes unexplained activity for human investigation. It must never label an employee as malicious or infer intent.

## Required evidentiary stance
- Detection and scoring must be deterministic and inspectable.
- The product must function without an LLM.
- An LLM may translate a structured evidence object into readable prose only after the deterministic engine is implemented and separately approved.
- The LLM must not calculate risk, infer guilt, or suppress alerts.
- All generated explanations must reference evidence identifiers.
- A deterministic fallback explanation must always exist.

## Claims policy
Every capability must be classified as one of:
- IMPLEMENTED
- SIMULATED
- PLANNED
- EXPERIMENTAL

Unsupported or forbidden claims include but are not limited to:
- zero false positives
- unmeasured accuracy
- arbitrary detection or containment latency
- autonomous containment
- production readiness
- live integration when using fixtures
- court-admissible evidence
- blockchain or immutable evidence without implementation
- guaranteed prevention
- malicious intent attribution

## Engineering discipline
- Use strict TypeScript.
- Keep domain logic independent of React.
- Avoid monolithic components.
- Do not add dependencies without justification.
- Never expose secrets in frontend code.
- Add tests before or alongside domain behavior.
- Preserve keyboard accessibility.
- Respect prefers-reduced-motion.
- Run typecheck, tests, and build after each milestone.
- Report exact failures and warnings.
- Never claim successful verification without proof that it ran.
- Never silently change an approved calculation or product claim.

## Documentation expectations
When creating or revising product documentation, keep it explicit about:
- product scope
- non-goals
- assumptions
- unresolved decisions
- data provenance
- evidence identifiers
- certainty and uncertainty
- what is simulated versus implemented

## File and repo safety rules
- Documentation-only tasks may create files under docs/ and the repo root.
- Do not create runtime code or infrastructure without approval.
- Do not create .env files or secrets.
- Do not commit or push during documentation-only work.

## Default posture
If a task requires a product decision not explicitly specified in the requirement, document the decision as required rather than inventing a resolution.
